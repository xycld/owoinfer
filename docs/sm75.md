# Turing (sm_75) support

MossInfer builds for NVIDIA compute capability 8.x (Ampere, Ada) and 12.x (Blackwell) by default. A build configured
with `-DMOSSINFER_SM75=ON` also carries a full set of Turing kernels and accepts compute capability 7.5 devices (RTX
20xx, T4, GTX 16xx), so a card such as an RTX 2080 8 GiB can run the whole pipeline: text encoder, DiT and VAE.

Turing has no bf16 tensor cores, no `cp.async`, no TF32 and only 64 KiB of shared memory per block, so the sm_75
kernel family is not a flag on the sm_80 one: it is a second implementation of every tensor-core kernel, compiled for
`sm_75` alone and dispatched at run time by the device's compute capability.

## Build

The Windows CUDA 13 preset builds a complete package and names it with a `-sm75` suffix:

```sh
cmake --preset windows-msvc-cuda13-sm75
cmake --build --preset windows-msvc-cuda13-sm75
ctest --preset windows-msvc-cuda13-sm75 -L '^cpu$'
cpack --config build-windows-msvc-cuda13-sm75/CPackConfig.cmake -B build-windows-msvc-cuda13-sm75
# -> build-windows-msvc-cuda13-sm75/mossinfer-2.0.0-windows-cu13-x86_64-sm75.zip
```

Any other preset takes the option too (`-DMOSSINFER_SM75=ON`), e.g. a Linux build from a custom preset; the ordinary
presets stay Ampere-and-newer. Without the option the engine refuses compute capability 7.5 exactly as before.

## What runs

| Component | sm_80+ build (unchanged) | sm_75 build |
|---|---|---|
| bf16 linears (DiT blocks and globals, text refiner, text encoder) | cuBLASLt bf16 tensor cores | fp16 tensor cores through cuBLASLt: weights are converted to fp16 once at load (or per streamed block), activations are converted in row chunks, accumulation stays fp32, the output is converted back to bf16 with the bias added in fp32 |
| Exact attention | FlashAttention-2 (bf16, `cp.async`) | a dedicated `m16n8k8` fp16 kernel with an online softmax (head_dim 128 non-causal varlen GQA for the DiT, head_dim 256 causal for the text encoder) |
| INT8 ConvRot GEMMs (`high` tier) | CUTLASS `m16n8k32` | CUTLASS `m8n8k16` (Turing's INT8 MMA), same epilogues; bit-exact against a host int32 reference |
| INT4 ConvRot GEMMs (`turbo` tier) | CUTLASS `m16n8k64` | the engine's existing INT4 → INT8 unpack fallback (bit-exact, the same path Hopper and Blackwell use) |
| 8-bit attention (`q8_fp16`, `q8_fp8`) | SageAttention kernels | not built: an unset `attention` resolves to `exact` with the reason saying so (the tier is otherwise unchanged) |
| VAE decode | TF32/bf16 CUTLASS implicit-GEMM convolutions, TF32 attention | fp32 SIMT convolutions and a fp32 attention kernel (reference precision; slower, see below) |
| GatedDeltaNet (text encoder) | chunked kernel (~85 KiB of shared memory) | a per-token recurrent kernel that fits 33 KiB; the same rule, fp32 |
| Other kernels (norm, RoPE, elementwise, samplers, group norm, latent preview, …) | compiled for sm_80+ | compiled for sm_75 and sm_80+ from the same source (pure SIMT) |

The DiT blocks run op by op on sm_75: the fused bf16 CUTLASS GEMMs need sm_80+ tensor cores, so the fused route and
its CUDA graphs are not used. Every block path produces the same image, so this only affects speed.

### Tiers on sm_75

`reference` (bf16 bundle), `high` (INT8 ConvRot DiT) and `turbo` (INT4 ConvRot DiT) all run. As on any device without
an 8-bit attention kernel, an unset `attention` resolves to `exact` and the report's `quality.reason` says
"(no 8-bit attention kernel on this device)"; a caller may still pass `attention=exact` explicitly. NVFP4 DiTs are
refused as on every non-Blackwell GPU.

## Performance

Measured on an RTX 2080 8 GiB (Turing, 46 SMs), MOSS-Image SFT, `balanced` mode, the bf16 bundle with the text encoder
streamed:

| Configuration | Size | Denoise step | Notes |
|---|---|---|---|
| bf16 bundle, `reference` | 256² | 0.80 s | 6.9 GiB device peak |
| INT8 DiT (`moss-infer quantize … --format int8`), `high` | 256² | **0.19 s** | 6.5 GiB peak, DiT resident |
| INT4 ConvRot DiT, `turbo` | 256² | **0.22 s** | 3.9 GiB peak |
| INT8 DiT, `high` | 512² | 0.63 s | 20 steps in 22 s total |
| INT8 DiT, `high` | 1024² | 3.8 s | 8 steps in 51 s total, 6.9 GiB peak |

The VAE decodes in fp32 on sm_75: about 0.4 s at 256², 1.6 s at 512² and 10–12 s at 1024². The bf16 text encoder is
roughly 3–5 s per prompt when streamed (its ~16 GB do not fit 8 GiB of VRAM); it is planned like on any other device.

## Numerics

- bf16 → fp16 is exact for values in fp16's normal range, and fp16 → bf16 recovers the original bf16 value, so the
  converted operands are the same numbers the sm_80 kernels see. Accumulation stays fp32 where the sm_80 kernel
  accumulates in fp32.
- Attention, GEMMs and the VAE therefore differ from an sm_80 run only in accumulation order and rounding, not in the
  values fed in. INT8 GEMM results are bit-identical (exact int32 accumulation).
- The reference vectors under `tests/data` are recorded on sm_89; as on sm_120, tests that compare against them run
  with noise-class gates off that architecture.
- Values outside fp16's range (|x| > 65504 or |x| < ~6e-5) do not survive the bf16 → fp16 conversion; the model's
  activations and weights are inside that range in practice.

## Verification

- `tools/sm75_check.cu` (not installed, built with `MOSSINFER_SM75=ON`) runs the Turing kernels against host
  references: dtype conversion, exact attention at both head dimensions and engine-shaped varlen/GQA cases, the fp16
  GEMM, the INT8 GEMM (bit-exact), and the VAE convolution and attention.
- `tests/unit/test_sm75.cpp` covers the build's presence and the in-place conversions on a device.
- The two refusals are exercised on the RTX 2080: `moss-infer generate --init-image …` and `--lora …` end with
  `not_supported` (CLI exit status 1, nothing written), and `moss-server` reports the same code in the `done` event.
- End to end on an RTX 2080: `moss-infer generate` and `moss-server` (protocol 2) produce the same PNG bytes for the
  `reference`, `high` and `turbo` tiers; the report's `quality.gpu_arch` is `sm_75`.
- A build with `MOSSINFER_SM75=OFF` compiles and links unchanged and keeps the same CPU test baseline.

## Not supported on sm_75 yet

- The 8-bit attention kernels (`q8_fp16`, `q8_fp8`): the tier default resolves to `exact`; passing an 8-bit mode
  explicitly is refused.
- Native INT4 MMA and NVFP4: INT4 files run through the INT8 unpack fallback (correct and bit-exact; the planner
  prices it at about 1.5× a native INT4 step); NVFP4 files are refused on every non-Blackwell GPU.
- The fused DiT blocks and their CUDA graphs (the blocks run op by op).
- img2img and inpainting: the VAE **encoder** is still an sm_80 kernel, so only text-to-image and hires fix run
  (`hires fix` uses the decoder). A request with `init_image` (or a `mask`) is refused up front with the code
  `not_supported` and a message saying why, so nothing is loaded or planned for it.
- Runtime LoRAs and control adapters: their GEMM kernels are built for sm_80+ only. A request that carries `loras` or a
  control adapter is refused up front with `not_supported`, again before any weight is read or uploaded.

The VAE decode is fp32 SIMT on sm_75, so a 1024² decode costs about 10–12 s; a future fp16 path would cut that.
